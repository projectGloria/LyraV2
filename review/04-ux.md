# UX and interface

The interface is carefully built — full keyboard support, focus trapping in modals, `aria-live` on the scan progress and library summary, a global `prefers-reduced-motion` block, artwork fallbacks with generated initials, and virtualized track lists whose CSS row height (`min-height: 62px` with `white-space: nowrap`) genuinely matches the `TRACK_ROW_HEIGHT = 62` the virtualizer assumes. The findings below are specific defects, not a general critique.

### [Medium] Three sidebar filter pills are dead controls

**Where:** `index.html:43-47`
**Trigger:** Click "Playlists", "Folders" or "Albums" in the library sidebar.
**Detail:**

```html
<button class="filter-pill active">Playlists</button>
<button class="filter-pill">Folders</button>
<button class="filter-pill">Albums</button>
```

They carry no `data-action` and no `data-*` hook, and `grep` finds no handler for `.filter-pill` anywhere in `renderer.js` — the only matches are CSS rules. They are nonetheless styled with hover, `:focus-visible` and `.active` states, sit inside `role="tablist"`, and the first is permanently marked active.
**Impact:** Three prominent, focusable, visually interactive controls that do nothing when clicked. Because "Playlists" is hard-coded active and the library does show playlists, the set reads as a working filter that is stuck — the user will click "Albums", see no change, and conclude the app is broken rather than unfinished. The `role="tablist"` without `role="tab"` children or `aria-selected` also misreports the structure to screen readers.
**Fix:** Implement the filters, or remove the markup until they exist. A disabled state with a tooltip is the middle option.
**Confidence:** Verified

### [Medium] The in-list search box forces the caret to the end on every keystroke

**Where:** `renderer.js:2239-2247`
**Trigger:** Type in the "Search in playlist" box, then click into the middle of what you typed and keep typing.
**Detail:** Each debounced input re-renders the whole content view — which destroys and recreates the input — and then restores focus with:

```js
input.focus();
input.setSelectionRange(input.value.length, input.value.length);
```

The caret is unconditionally moved to the end, and the selection is collapsed.
**Impact:** Mid-string editing is impossible: correcting a typo at the start of the query puts every subsequent character at the end instead. Selecting text to replace it also fails, since the selection is collapsed 90 ms later.
**Fix:** Capture `selectionStart`/`selectionEnd` before the re-render and restore those values, or update the results without re-rendering the input.
**Confidence:** Verified

### [Medium] Dragging a song downward appears to do nothing

**Where:** `renderer.js:1640` — full analysis in `01-bugs.md`.
**Impact stated as UX:** Because upward drags work correctly and downward drags silently no-op or under-shoot by one, reordering feels non-deterministic rather than broken, which is the harder failure for a user to diagnose or report.

### [Low] "Show all" in the Credits card is a non-interactive span

**Where:** `renderer.js:901`
**Detail:** `<span>Show all</span>` sits in a `.card-heading` next to "Credits", styled as the affordance it isn't. There is no handler and no expanded credits view.
**Impact:** Same class of problem as the filter pills, at lower prominence — an advertised action that cannot be taken.
**Fix:** Remove it, or wire it to a credits expansion.
**Confidence:** Verified

### [Low] Reordering silently clears the active in-list search

**Where:** `renderer.js:1637` (`state.listQuery = '';` in `reorderSelectedTracks`)
**Trigger:** Filter a playlist, drag one of the filtered results to a new position.
**Detail:** The reorder is applied against the full track list (correct — the drop target's position in the unfiltered list is the meaningful one), but the search box is then cleared without explanation and the list snaps back to showing everything.
**Impact:** The user loses their filter and their place in the list mid-task, with no indication why. The reorder they just performed also becomes hard to verify, since the view they were working in is gone.
**Fix:** Keep the query and re-render the filtered view; if reordering under a filter is genuinely ambiguous, disable dragging while a filter is active and say so.
**Confidence:** Verified

### [Low] Renaming a playlist renames the user's folder on disk with no warning

**Where:** `main.cjs:389-391`, dialog markup at `index.html:137-148`
**Detail:** The playlist editor presents "Title" as a display-name field. Saving calls `fs.renameSync` on the actual directory in the user's music folder, after passing the name through `sanitizePlaylistName` — which silently strips `< > : " / \ | ? *`, control characters and trailing dots.
**Impact:** A rename here mutates the user's filesystem, invalidating external references (other players' libraries, backup sets, sync tools). Characters are silently dropped, so the saved title can differ from what was typed with no feedback. The success toast — "Playlist updated in your music folder" — is the only hint, and it appears after the fact.
**Fix:** State in the dialog that the title is the folder name, and show the sanitized result before saving when it differs from the input.
**Confidence:** Verified

### [Low] Scan progress announces on every update via `aria-live`

**Where:** `renderer.js:233` (`role="status" aria-live="polite"`), updated from `updateScanProgressDom`
**Detail:** The progress region's text is rewritten on each throttled progress tick (roughly every 80 ms during the metadata phase), including a per-file `detail` line.
**Impact:** Screen reader users get a continuous stream of announcements naming each file for the duration of a scan, which on a large library is minutes of speech that cannot be interrupted usefully.
**Fix:** Keep `aria-live` on a coarse summary that changes only at stage boundaries or 10% increments, and mark the per-file detail `aria-hidden`.
**Confidence:** Probable — the DOM behaviour is verified; the announcement cadence depends on the screen reader's coalescing.
